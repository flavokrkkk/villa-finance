# Villa Finance — прототип финансовой аналитики портфеля вилл

Рабочий прототип: загрузка → проверка качества → расчёты → dashboard с фильтрами по объекту и периоду.
Данные синтетические (`data/raw`, из задания), валюта IDR, период сентябрь–октябрь 2026.

**Коротко о результате (сен–окт 2026, все 20 объектов, признание по ночам):**

| Показатель | IDR |
|---|---:|
| Gross bookings | 1 252 752 856 |
| OTA fees | 183 108 072 |
| Management fees | 222 630 399 |
| Операционные расходы (начислено) | 49 462 041 |
| **Owner balance — оценка** | **797 552 344** |
| Ожидается к получению (net − OTA) | 1 069 644 784 |
| Получено денег в периоде | 485 396 549 |

Главное: **owner balance нельзя считать точным**. 85 из 146 действующих бронирований пересекаются по датам
с другими на той же вилле (147 «двойных» ночей; у V003 загрузка 110%). Если учитывать только записи без
замечаний, owner balance — **258,6 млн** вместо 797,6 млн. Реальное значение лежит в этом диапазоне
и зависит от того, какие из пересекающихся броней настоящие. Это вопрос к источнику данных (PMS), а не к формулам.

## Быстрый старт

Нужен Python 3.10+ (проверено на 3.12).

```bash
make setup          # venv + зависимости
make run            # dashboard → http://localhost:8501
make test           # 26 тестов
make report         # CLI-сводка + CSV в output/
make ingest         # демонстрация идемпотентного импорта (запустите дважды)
```

Без make: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/streamlit run app.py`.

## 1. Dashboard

учитывать ли записи «на проверке», дата оценки поступлений (as-of), отсрочка платежа.

| Вкладка | Что показывает |

| Обзор | KPI: gross bookings, OTA fees, management fees, opex, owner balance (оценка), ожидаемые и полученные деньги, разница, загрузка, отмены. Каскад «gross → owner balance», owner balance по объектам, таблица по объектам с выгрузкой CSV |

## 2. Финансовая методология

### Две оси, которые не смешиваются

| | Начисление (accrual) | Денежный поток (cash) |
|---|---|---|
| Вопрос | Сколько заработано за период | Сколько денег пришло за период |
| Дата | ночь проживания | `payment_date` |
| Источник | reservations + commission_rules + expenses | payments |
| Показатели | gross bookings, OTA fees, management fees, opex, owner balance | получено, расходы оплаченные |

Связывает их **сверка**: по каждой брони «ожидается к получению» сравнивается с суммой платежей.
Разница периода (`ожидается − получено`) — это не «убыток», а сумма трёх эффектов: время (деньги придут позже
или пришли за другой период), неоплаты и ошибки данных.

### Формулы

Для брони: `n` — число ночей (`check_out − check_in`), доля ночи = `1/n`. Активные статусы: `confirmed`, `modified`.

| Показатель | Формула |
|---|---|
| Gross bookings | Σ `gross_booking_value` активных броней × доля ночей, попавших в период |
| Возвраты | Σ `refund_amount` активных броней (частичные возвраты) × доля ночей |
| Удержано при отмене | Σ (`gross − refund`) отменённых броней × доля ночей (штраф за отмену; в данных = 0) |
| Net revenue | gross bookings − возвраты + удержано при отмене |
| OTA fees | Σ `ota_fee` активных броней × доля ночей; по отменам — 0 (см. A4) |
| Management fee | Σ по ночам: ставка, действующая **на дату ночи**, × net revenue ночи. База `gross_booking_value` — OTA-комиссия **не** вычитается (`note: OTA fees are separate`) |
| Opex (начисление) | Σ `expenses.amount` по `expense_date` в периоде, статусы `paid` и `pending` |
| **Owner balance (оценка)** | net revenue − OTA fees − management fee − opex |
| Ожидается к получению | net revenue − OTA fees |
| Получено | Σ `payments.amount` по `payment_date` в периоде (без исключённых платежей) |
| Загрузка | проданные ночи / (дни периода × объекты) — всегда по физическим ночам |

Месяцы складываются в период без потерь — это проверено тестом (`test_months_add_up_to_whole_period`).

### Даты и признание

* **По умолчанию — по ночам проживания (pro-rata).** Услуга проживания оказывается каждую ночь, поэтому бронь
  29.09–02.10 даёт 2/3 выручки в сентябре и 1/3 в октябре. Это корректно для P&L по месяцам и для отчёта
  собственнику за период.
* Альтернативы в фильтре — «целиком на дату заезда» и «целиком на дату выезда»: многие PMS и owner statements
  считают по check-out. Сравнение показывает чувствительность (сентябрь, gross, млн IDR):
  по ночам 712,7 · по заезду 751,0 · по выезду 638,8. Какой метод в договорах — вопрос к CFO.
* Ночь датируется днём заезда в эту ночь; день выезда — не ночь.
* Ставка management fee берётся на дату ночи — если ставка поменяется посреди проживания, каждая ночь получит свою.
* Расходы признаются по `expense_date`. Даты фактической оплаты расхода нет, поэтому «оплаченные расходы» —
  это статус `paid` на дату выгрузки, а не денежный поток по датам.

### Отмены и возвраты

* `cancelled` не даёт выручки, ночей и загрузки. Полная сумма отмен показывается справочно («Отмены (gross)»).
* Если по отмене вернули не всё (`refund < gross`), остаток — доход (штраф за отмену), с него начисляется
  management fee; запись уходит на проверку. В выданных данных все отмены возвращены полностью.
* Частичный возврат по активной брони уменьшает net revenue и базу management fee; запись уходит на проверку.
* `refund > gross` — невозможная арифметика, запись исключается (R0072).

### Почему формула «ожидается к получению» — `gross − OTA fee − refund`

Это подтверждено данными: у **всех 66** броней, по которым есть платёж, сумма платежа совпадает с
`gross − ota_fee − refund` до рупии (`test_payment_equals_gross_minus_ota_minus_refund`). Значит, канал
перечисляет деньги за вычетом своей комиссии, а management fee компания удерживает уже из полученного.
По 12 отменам платёж 0 — канал ничего не удержал, отсюда допущение A4.

### Owner balance — оценочный

Это **начисленная доля собственника за период**, а не сумма к выплате. Для точного значения не хватает:

1. Решения по 85 пересекающимся броням — какая из них реальная (разброс 259–798 млн).
2. Платежей по 68 броням с нечётными номерами — похоже на неполную выгрузку (см. ниже).
3. Условий договора: на кого ложатся какие расходы, есть ли фиксированные платежи, минимальная гарантия.
4. Налогов: включает ли `gross_booking_value` налог (на Бали — PB1 10%) и сервисный сбор, считается ли
   комиссия до или после налога.
5. Уже сделанных выплат собственникам, авансов, депозитов, остатка на начало периода.
6. Курсов валют (одна бронь в USD) и правил конвертации.

### Допущения

| # | Допущение | Почему |
|---|---|---|
| A1 | Признание по ночам проживания | экономическая суть услуги; переключается в фильтре |

## 3. Качество данных

### Принцип

Данные не исправляются молча. У каждой записи — статус и журнал замечаний с адресом (файл, строка, ID),
правилом, решением и суммой под риском.

* **exclude** — запись не участвует в расчётах: её нельзя корректно посчитать или отнести к объекту.
* **review** — запись участвует в расчётах, но уходит на проверку: по отдельности данные правдоподобны,
  но конфликтуют с другими записями.
* **info** — системное наблюдение или вопрос к бизнесу, на расчёт не влияет.

Полный журнал — вкладка «Качество данных» или `output/dq_issues.csv`.

### Найденные ошибки и решения

| Запись | Проблема | Решение | Почему |
|---|---|---|---|
| R0015 (строка 152) | Полный дубль строки 16 | **exclude** копию | иначе выручка удваивается; оригинал остаётся |
| P0075 (строка 77) | Полный дубль платежа | **exclude** копию | иначе cash завышен на 12,2 млн |
| R0034, P0017 | Объект `V999` не существует | **exclude**, review маппинга | нельзя отнести к собственнику; 14,5 млн gross и 12,7 млн cash вне отчёта |
| E0017 | Объект `V777` не существует | **exclude** | расход 0,8 млн не на что отнести |
| R0061 | Валюта `USD` при базовой IDR; сумма 4 280 874 за 4 ночи — это ≈1,07 млн за ночь, обычная цена в IDR (медиана по портфелю 1,77 млн), а в USD было бы ≈1 млн долларов за ночь | **exclude** до подтверждения | курса нет; если это опечатка кода валюты — исправить в источнике |
| R0072 | `refund 7 970 068 > gross 7 070 068` при статусе `confirmed`; платёж 0 | **exclude** | вероятно, это отмена с опечаткой (одна цифра: 7**9**70 vs 7**0**70) и неверным статусом; включать нельзя — дала бы отрицательную выручку |
| R0102 | `ota_fee = −100 000`; платёж P0051 = gross + 100 000 | **exclude**; P0051 — review | отрицательной комиссии не бывает; платёж больше стоимости брони — подтверждает, что ошибка в источнике |
| P0036, P0051 | Платежи по исключённым броням | **review** | деньги учитываются в cash, но не сверяются с начислением |
| 85 броней | Пересечение дат на одной вилле (подробно ниже) | **review** | физически невозможно, но какая бронь ложная — по данным не определить |
| 31 бронь Direct | Прямая бронь с `ota_fee` 12–17% | **info** | вопрос к CFO: что это за удержание |
| 7 платежей | Нулевые суммы (6 отмен + R0072) | **info** | записи без движения денег |
| payments.csv | Платежи есть только у броней с чётным номером (75 из 150), у нечётных — ни одного | **info** | такой паттерн не бывает у реальных неплатежей — скорее неполная выгрузка; 562,5 млн «не получено» нужно подтвердить |

Проверялись и не найдены: битые даты и суммы, `check_out ≤ check_in`, неизвестные статусы, похожие дубли
расходов (тот же объект/дата/категория/сумма с разными ID), несовпадение объекта платежа и брони,
пересечения и пробелы в ставках комиссии. Эти правила работают и покрыты тестами на синтетических данных.

### Пересекающиеся периоды

Вилла одна, поэтому две действующие брони не могут занимать одну ночь. Отмены в проверке не участвуют,
касание (выезд = заезд) пересечением не считается, исключённые записи (например, дубль R0015) тоже не участвуют.

* 85 броней, 147 «двойных» ночей; у V003 67 проданных ночей за 61 день (загрузка 110%).
* Подтипы в журнале:
  * **те же даты** — R0033 / R0056 (V008, 25.09–02.10, разные суммы): возможный дубль из разных каналов;
  * **modified-запись** — R0145↔R0126, R0146↔R0027/R0112, R0148↔R0038/R0045, R0149↔R0150: похоже,
    изменённая бронь пришла новой записью, а старая версия не удалена или не отменена;
  * обычные пересечения на 1–7 ночей.
* Решение: review, по умолчанию учитываются, в dashboard видно, какая доля gross на них приходится (64%).
  Автоматически выбирать «правильную» бронь не стал: любое правило (последняя по `updated_at`, оплаченная
  и т. п.) на этих данных было бы догадкой. Нужен календарь PMS как источник истины и ссылка
  `original_reservation_id` у изменённых броней.

## 4. Архитектура

Подробно — [docs/architecture.md](docs/architecture.md) (схема Mermaid, повторный импорт, аудит, доступы).

```
Источники (PMS, OTA payouts, банк, учёт, договоры, курсы)
   → Загрузка (коннекторы, неизменяемый landing + SHA-256 файла)
   → Проверка и хранение (staging с версиями, DQ-правила, карантин и очередь review, core-модель)
   → Расчёты (dbt: начисление по ночам, комиссии, сверка; закрытие периода)
   → Dashboard (BI с RLS по собственнику) + отчёты собственникам + алерты
```

* **Повторный импорт без дублей**: хэш файла → хэш записи по натуральному ключу → версии (SCD2).
  В прототипе работает (`villa_finance/ingest.py`, `make ingest` дважды): второй прогон добавляет 0 записей,
  изменённая бронь становится новой версией (`tests/test_ingest.py`).
* **Аудит**: append-only хранение, происхождение каждой записи (файл, строка, батч, кто загрузил),
  журнал решений по DQ, снимок входных данных и версия расчёта у каждого отчёта.
* **Доступы**: роли (финансы, операции, аналитик, собственник, аудитор), RLS по `owner_id`, SSO,
  секреты в vault, персональные данные гостей не попадают в витрины.

## 5. Решения и компромиссы

### Выбор технологий

* **Python + pandas** для расчётов: формулы и правила DQ — обычный код, их можно протестировать,
  отревьюить и потом перенести в SQL/dbt один к одному. BI-инструмент с формулами в UI так проверить нельзя.
* **Streamlit** для dashboard: рабочий интерфейс с фильтрами за минимальное время, запускается одной командой,
  без сервера БД и токенов.
* **SQLite** для демонстрации идемпотентного импорта: встроен в Python, ничего не нужно ставить.
* Расчётное ядро (`villa_finance/`) не зависит от UI — тот же код используют dashboard, CLI и тесты.

### Ограничения прототипа

* Расчёт в памяти по CSV; dashboard не пишет в хранилище (импорт в SQLite — отдельная демонстрация).
* Одна валюта (IDR) — записи в другой валюте исключаются, а не конвертируются.
* Нет налогов, выплат собственникам, остатков на начало периода — owner balance только оценка.
* Очередь review не интерактивная: решения по замечаниям не сохраняются.
* Нет авторизации и разграничения доступа.
* Pro-rata в float: при выпуске отчётов нужно округление до рупии с распределением остатка (largest remainder).

### Риски

* **Пересечения броней (64% gross)** — главный риск: выручка и owner balance могут быть завышены до 3 раз.
* **Неполная выгрузка платежей** — 562,5 млн «не получено» может оказаться артефактом экспорта, а не долгом.
* **Методика признания** не согласована с договорами — разные методы дают ±10% по месяцу.
* **Ставки комиссии** заданы только на 01.09–31.12.2026 — брони за пределами этого периода получат
  предупреждение NO_COMMISSION_RULE и нулевую комиссию до обновления справочника.

### Три следующих шага

1. **Источник истины по броням.** Подключить PMS/channel manager по API с `original_reservation_id`
   и историей изменений; разобрать 85 пересечений с операционной командой. Это убирает главный риск.
2. **Хранилище и регламентная загрузка.** PostgreSQL + dbt + оркестратор: перенести правила DQ в dbt-тесты,
   включить версионирование и очередь review с сохранением решений.
